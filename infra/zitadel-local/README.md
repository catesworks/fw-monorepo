# Zitadel (local, for OrbStack/Docker)

A from-scratch local Zitadel instance for the Fleetworks suite (chorus,
helmsman, rolodex, warden, yellow-pages). In production, each app already
federates login through a hosted Zitadel instance at `account.fleetworks.dev`
via Supabase's custom OIDC provider. Locally, each app's Supabase stack runs
auth standalone today — there is no local Zitadel. This directory is that
missing piece: a disposable, fully-bootstrapped Zitadel + Postgres stack you
can bring up with one command.

**This stack is standalone.** It is not yet wired into any of the 5 apps'
local dev flow (no app's `.env.local` reads from here automatically). Wiring
it in is separate, future work — see [Not yet wired in](#not-yet-wired-in)
below.

This is local dev tooling, not an npm package. It does not participate in the
pnpm workspace, changesets, or the publishing flow in the rest of this repo.

## What's here

- `docker-compose.yml` — Traefik (reverse proxy) -> `zitadel-api` +
  `zitadel-login` (Next.js Login v2 UI) -> Postgres. This is upstream
  Zitadel's own [Docker Compose stack](https://zitadel.com/docs/self-hosting/deploy/compose),
  pinned to `v4.17.1` and extended with `ZITADEL_FIRSTINSTANCE_*` bootstrap
  env vars so the org, admin user, and a seed-bot service account all exist
  the moment the stack becomes healthy — no Console clicking required.
- `.env.example` — copy to `.env` before starting. Documents every variable,
  including the insecure-by-design local defaults.
- `seed.ts` — creates the "Fleetworks Suite" project, 5 per-app OIDC clients,
  2 project roles, and 2 test users, then writes `generated-client-env.md`.
- `generated-client-env.md` — generated by `seed.ts`, gitignored. Per-app
  issuer/client_id/JWKS values.

## Port

Zitadel listens on **`http://localhost:8080`** (console + all APIs, via
Traefik). This was chosen because it does not collide with any of the 5
apps' existing local ports:

| App          | Web port | API port |
| ------------ | -------- | -------- |
| helmsman     | 3025     | 4025     |
| chorus       | 3021     | 4021     |
| warden       | 3020     | 4020     |
| rolodex      | 3013     | 4013     |
| yellow-pages | 3023     | 4023     |

> If port 8080 is already taken by something else on your machine (e.g.
> another local stack's `process-compose` UI), override it per-run:
> `PROXY_HTTP_PUBLISHED_PORT=8089 ZITADEL_EXTERNALPORT=8089 docker compose up -d --wait`
> (and pass `ZITADEL_BASE_URL=http://localhost:8089` to `seed.ts`). This is
> exactly how this stack was verified end-to-end (see below) — 8080 was busy
> on the build machine.

## Bring it up

```bash
cd infra/zitadel-local
cp .env.example .env
docker compose up -d --wait
```

`--wait` blocks until every service (Postgres, `zitadel-api`, `zitadel-login`,
the Traefik proxy) reports healthy — including Zitadel's own `/app/zitadel
ready` healthcheck. OrbStack runs this exactly like any other `docker compose`
host; no special syntax is needed.

Bootstrap only runs once, against an empty Postgres volume. Re-running
`docker compose up -d` against an existing volume does **not** re-apply
`ZITADEL_FIRSTINSTANCE_*` changes — to start over, wipe everything with:

```bash
docker compose down -v
```

## Seed it

```bash
node seed.ts
```

Requires Node >=22 (tested on Node 24) — no npm install, no dependencies.
Node's built-in TypeScript type-stripping runs the file directly.

The script:

1. Reads the seed-bot's Personal Access Token straight out of the running
   container via `docker compose cp` (the Zitadel image ships only the
   `zitadel` binary — no shell — so `docker compose exec ... cat` does not
   work here; `cp` talks to the container filesystem through the daemon
   instead).
2. Finds the "Fleetworks" org (created by `FIRSTINSTANCE` bootstrap).
3. Creates the "Fleetworks Suite" project.
4. Creates two project roles: `admin`, `member`.
5. Creates 5 OIDC applications — **one client per app, not one shared
   client** — each a public Auth Code + PKCE client (no secret) scoped to
   that app's own `http://localhost:<port>/auth/callback`.
6. Creates 2 test users and grants them project roles.
7. Writes `generated-client-env.md` with the per-app env values, using the
   live instance's own `/.well-known/openid-configuration` for the
   issuer/JWKS/endpoint URLs (never hardcoded).

Every step is check-before-create, so re-running the script is safe and
prints "already exists" instead of failing or duplicating anything. The one
exception is project-role grants on users, which are created best-effort: a
conflict response is treated as "already granted" without re-verifying the
exact role set matches.

### Test users

| Username                     | Password       | Role     |
| ---------------------------- | -------------- | -------- |
| `test-admin@fleetworks.dev`  | `TestAdmin1!`  | `admin`  |
| `test-member@fleetworks.dev` | `TestMember1!` | `member` |
| `test-viewer@fleetworks.dev` | `TestViewer1!` | `member` |

The third account exists for apps whose own RBAC ladder has three rungs (e.g.
helmsman's `org:admin` / `org:contributor` / `org:viewer`); its Zitadel role is
`member` because this instance only models two. Each app maps these usernames
onto its own roles in its `DEV_SEED_ACCOUNTS`.

**Local dev use only.** These are throwaway credentials seeded into a
disposable local instance — never real secrets, never used anywhere but this
stack.

### Human admin

Bootstrapped via `FLEETWORKS_ADMIN_EMAIL` / `FLEETWORKS_ADMIN_PASSWORD` in
`.env` (defaults: `admin@fleetworks.local` / `FleetworksLocal1!`). Log in to
the Console at `http://localhost:8080/ui/console`.

## Generated env values

After seeding, `generated-client-env.md` (gitignored — it's a regenerable
local artifact tied to one specific bootstrap, not a secret) has one block
per app, e.g.:

```
## Yellow Pages

ZITADEL_ISSUER=http://localhost:8080
ZITADEL_CLIENT_ID=<numeric client id>
ZITADEL_JWKS_URI=http://localhost:8080/oauth/v2/keys
ZITADEL_AUTHORIZATION_ENDPOINT=http://localhost:8080/oauth/v2/authorize
ZITADEL_TOKEN_ENDPOINT=http://localhost:8080/oauth/v2/token
ZITADEL_REDIRECT_URI=http://localhost:3023/auth/callback
ZITADEL_POST_LOGOUT_REDIRECT_URI=http://localhost:3023
```

Client IDs for public PKCE clients are not secret, but never commit the
machine key JSON or the admin/seed-bot PAT that live inside the container at
`/zitadel/bootstrap/`.

## Not yet wired in

Nothing in any of the 5 app repos reads from this stack today. Actually
pointing an app's local Supabase-standalone auth at this Zitadel instance
(mirroring the production "Sign in with Fleetworks" custom OIDC provider
flow) is separate, future work, tracked by the broader SSO/SAML/SCIM
platform-identity plan. This directory only stands the identity provider
itself up and proves it mints valid tokens.

## Verifying it works yourself

Beyond `docker compose ps` showing all four services healthy, you can mint a
real token headlessly (no browser) for a seeded test user against a seeded
client, using Zitadel's own Session API + OIDC callback API — the documented
way to drive the Auth Code + PKCE flow from a script:

1. `SessionService/CreateSession` with `checks: { user: { loginName }, password: { password } }`
   using the seed-bot's PAT — returns a `sessionId` + `sessionToken`.
2. `GET /oauth/v2/authorize` with your own PKCE `code_challenge` — without an
   existing browser session, this redirects to the Login UI with an
   `authRequest=<id>` query param. Capture it from the `Location` header;
   don't follow the redirect.
3. `OIDCService/CreateCallback` with that `authRequestId` and the session
   from step 1 — **requires the `login-client.pat`** (also written to
   `/zitadel/bootstrap/` by this same compose stack), not the seed-bot's PAT;
   only the login-client service account has permission to finalize auth
   requests. Returns a `callback_url` containing a real authorization `code`.
4. `POST /oauth/v2/token` with `grant_type=authorization_code`, the `code`,
   and your `code_verifier` — a normal PKCE token exchange, no special
   headers needed.

The resulting `id_token`'s `iss` and `azp`/`client_id` claims match this
instance's issuer and the seeded app's client ID, and `sub` resolves via
`/oidc/v1/userinfo` back to the exact seeded test user.

## Notes / deviations

- **Pinned version, not `latest`.** `ZITADEL_VERSION=v4.17.1` (current stable
  at time of writing) rather than a floating `:latest` tag, so a fresh
  `docker compose up` is reproducible instead of silently picking up
  whatever shipped most recently.
- **Postgres, not CockroachDB** — `ZITADEL_DATABASE_POSTGRES_DSN` against the
  bundled `postgres:17.10-alpine` service, per the task requirement.
- **No shell in the `zitadel-api` image.** `docker compose exec ... sh -c` /
  `cat` fail with `ENOENT`; both `seed.ts` and the manual verification steps
  above use `docker compose cp` instead, which talks to the container
  filesystem directly through the Docker daemon.
- **PAT over JSON machine key.** Both are bootstrapped
  (`ZITADEL_FIRSTINSTANCE_ORG_MACHINE_MACHINEKEY_*` and `..._PAT_...`), but
  `seed.ts` authenticates with the PAT — a ready-to-use bearer token — rather
  than signing a JWT-profile assertion with the machine key. Far simpler and
  just as valid for a throwaway local script; the machine key still exists at
  `/zitadel/bootstrap/fleetworks-seed-bot-key.json` inside the container if
  ever needed for a JWT-profile grant.
- **Connect-RPC endpoint shape.** Zitadel's v2 "resource" APIs
  (`project.v2`, `application.v2`, `user.v2`, `authorization.v2`, `org.v2`,
  `session.v2`, `oidc.v2`) are unary Connect-RPC services callable over plain
  HTTP as `POST /<fully.qualified.package>.<Service>/<Method>` with a JSON
  body and a Bearer token — there is no separate REST path scheme for them
  like the older, now-deprecated `/management/v1/...` API uses. This isn't
  documented as a plain curl-able REST reference anywhere obvious; it was
  confirmed empirically by running `seed.ts` against a live instance.
- Dropped upstream's optional `redis` (cache) and `otel-collector`
  (tracing) services/profiles from `docker-compose.yml` — neither is needed
  for local dev, and both are one-line re-additions from the
  [upstream compose file](https://raw.githubusercontent.com/zitadel/zitadel/main/deploy/compose/docker-compose.yml)
  if ever wanted.
