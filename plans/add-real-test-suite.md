## RALPLAN-DR Summary (short mode)

### Principles
1. Match the existing toolchain — ESM-native (`"type": "module"`), TS-native, no new bundler paradigm alongside tsup/esbuild.
2. One test framework across the whole monorepo — packages should not diverge on tooling. *(Explicitly a secondary/weaker driver at this 2-package scale — see Decision Drivers; it does not by itself invalidate alternatives.)*
3. `turbo run test` must see the real dependency graph, and the fix for that must not touch what gets published to npm.
4. Fast local + CI feedback — unit-level tests colocated with `src`, no e2e scope creep.
5. No fake completion — no `.skip`/`.only`/stub tests, no cache-hidden false-greens, no shallow assertions; every test must assert real, currently-true behavior and fail if that behavior regresses.

### Decision Drivers (top 3)
1. Toolchain compatibility (ESM-native, TS-native, must exercise React 19 components in `ui`, including interactive/click-gated state).
2. Low setup/maintenance overhead — one config, not N per-package configs, and no new runtime `dependencies` surfaced to consumers.
3. CI already invokes `pnpm test` (`.github/workflows/ci.yml:27`) after `pnpm build` — needs to become a real signal without touching the release path (`changeset publish` → `npm publish`) or the published manifest.

### Viable Options

**Option A: Vitest, one root config with `test.projects` (recommended)**
- Pros: native ESM/TS support (no transform fights with `"type": "module"`), resolves this repo's existing `./apps.js`-style relative specifiers to `.ts` sources natively, a `jsdom` project can exercise `AppSwitcher`'s click-to-open menu (real DOM interaction), one config file total.
- Cons: adds `jsdom` + Testing Library as devDependencies to `ui`, and `vitest` as a devDependency to both packages + root (devDependencies only — no change to either package's published runtime `dependencies`).

**Option B: Jest**
- Pros: extremely mature ecosystem, huge docs/community.
- Cons: ESM support is still friction-heavy (`--experimental-vm-modules` / `ts-jest` ESM mode) against a repo that just adopted root `"type": "module"`; duplicates a transform pipeline tsup's esbuild already provides.

**Option C: Node built-in `node:test`**
- Pros: zero added *dependencies of any kind* for `suite-nav`; fits its "zero dependencies" description literally, including devDependencies.
- Cons: two decisive technical blockers for `ui` — (1) `AppSwitcher.tsx`'s entire `role="menu"` list (lines 50-99, about half the component) only renders after a click; `renderToStaticMarkup` cannot reach that state. (2) Node's built-in TS stripping does not rewrite `.js` import specifiers to `.ts`; this repo's `suite-nav/src/index.ts:1` and `ui/src/index.ts:1-8` use `.js`-style specifiers by convention, and `node:test` cannot resolve them without either enabling `allowImportingTsExtensions` and rewriting every specifier, or fighting the existing convention.

**Option C': Hybrid — `node:test` for `suite-nav`, Vitest for `ui`**
- Explicitly considered and rejected. Its only real advantage over Option A is that `suite-nav`'s devDependencies stay literally empty — but devDependencies are invisible to consumers regardless (see M6 above), so this buys nothing observable. Its cost is real: two test runners, two invocation styles, two report formats, and two things to keep in sync as the repo grows — for a repo currently at 2 packages and under 300 lines of source. Rejected on maintenance-cost grounds, not on Principle 2 alone.

**Invalidation rationale:** Option C (and its hybrid variant C') are invalidated on two verified technical blockers for `ui` (interactive/hidden-by-default content unreachable via static rendering; incompatible with the repo's existing `.js`-specifier convention), not on "one framework" aesthetics. Option B is invalidated because its ESM story fights the root `"type": "module"` change and duplicates tsup's esbuild transform. Option A is the only option that covers `ui`'s real interactive surface and resolves the repo's existing import style unmodified; its dependency cost (devDependencies only, zero published-consumer impact) is the honest trade, not a differentiator to oversell.

**Resolver-fix alternative considered and rejected:** a narrower-looking fix — a root `pnpm.overrides: { "@fleet-works/suite-nav": "workspace:*" }` — was also considered for Step 0, since it names exactly one package instead of flipping a workspace-wide flag and can never touch `packages/ui/package.json`. It was rejected on a verified, non-obvious mechanism: `turbo` matches each manifest's declared range against the *lockfile importer's `specifier`* to build its task graph, and `pnpm.overrides` rewrites that `specifier` (to `workspace:*`) rather than leaving it as `^0.1.0` — which severs the turbo edge just as badly as the original bug (confirmed by reproduction: `@fleet-works/ui#build deps: []` under the overrides approach). `linkWorkspacePackages: true` instead changes only the resolved `version` in the lockfile, leaving `specifier: ^0.1.0` intact for turbo to match against the unchanged manifest — the actual reason it's the right fix, stronger than "resolver not manifest" alone.

### 1. Root: single Vitest config, Vitest 4 `test.projects`
- Add root devDependency: `vitest` (pin latest 4.x — introduces `test.projects`).
- Add root `vitest.config.mts` (`.mts` is a naming preference only — verified it does **not** actually silence any warning under this repo's root `"type": "module"`, `.ts` works identically) with two **named** projects, each with an **absolute** `root` (via `import.meta.dirname`, available under Node ≥22, actually ≥20.11 upstream but this repo's `engines.node` is already `>=22`). Literal shape:
  ```ts
  import { defineConfig } from 'vitest/config';
  import path from 'node:path';

  export default defineConfig({
    test: {
      projects: [
        { test: { name: 'suite-nav', root: path.join(import.meta.dirname, 'packages/suite-nav'), environment: 'node', include: ['src/**/*.test.ts'] } },
        { test: { name: 'ui', root: path.join(import.meta.dirname, 'packages/ui'), environment: 'jsdom', setupFiles: ['./src/vitest.setup.ts'], include: ['src/**/*.test.{ts,tsx}'] } },
  ```

## Risks and Mitigations
- **Risk:** `linkWorkspacePackages: true` is workspace-wide and could change resolution for some other, currently-registry-resolved dependency. **Mitigation:** this workspace has exactly one internal cross-package dependency (`ui` → `suite-nav`); verify with `pnpm update @fleet-works/suite-nav --filter @fleet-works/ui` + `turbo run build` + `turbo run typecheck` pass before proceeding, per Verification Steps.
- **Risk (corrected mechanism):** the resolver-layer link is conditional on `suite-nav`'s local version still satisfying `ui`'s declared `^0.1.0` range. If `suite-nav` is bumped to `0.2.0` while `ui`'s range stays `^0.1.0`, a plain `pnpm install` **silently reverts** the lockfile entry back to the stale registry `0.1.0` copy and the turbo `ui#build → suite-nav#build` edge disappears — with no error, and the link does **not** self-heal on a later `pnpm install`; only an explicit `pnpm update --filter` restores it. Local tests would then silently start passing against the stale published tarball again, exactly the original C1 problem returning through a side door. **Mitigation:** in the normal release flow this is a non-issue — `changeset version`'s `updateInternalDependencies` already rewrites `ui`'s range in lockstep when `suite-nav` bumps, so the range and the link stay in sync automatically; the residual risk is only a manual/out-of-band version edit bypassing changesets. The repeatable acceptance criterion (`turbo run build --dry=json` still shows the edge) catches a silent reversion if it ever happens.
- **Risk:** applying `saveWorkspaceProtocol: false` + `linkWorkspacePackages: true` requires `pnpm update @fleet-works/suite-nav --filter @fleet-works/ui` rather than a plain `pnpm install`, which is easy to skip or get wrong. **Mitigation:** Step 0's verification explicitly names this exact command and its expected outcome (lockfile `version` becomes `link:../suite-nav`, `node_modules` symlink resolves to `../../../suite-nav`, manifest range unchanged at `^0.1.0`).
- **Risk:** `@testing-library/react` version incompatible with React 19 peer deps. **Mitigation:** pin `@testing-library/react@^16`; verify `pnpm install` resolves without `--force`/overrides.
- **Risk:** `jsdom` unpinned resolves to a major requiring a Node version this repo's CI/local dev doesn't guarantee, hard-failing install under `engine-strict=true`. **Mitigation:** pin `jsdom@^29` (Step 3) — verified compatible with CI's `node-version: 22` and any local Node ≥22.13.
- **Risk:** root `vitest.config.mts` edits don't invalidate turbo's `test` cache, allowing a silently-broken config to replay a stale pass. **Mitigation:** `test.inputs: ["$TURBO_DEFAULT$", "$TURBO_ROOT$/vitest.config.mts"]` on the `test` task in `turbo.json` (Step 1) — scoped to `test` only, so `build` isn't needlessly invalidated too.
- **Risk:** `tokens.test.ts` becomes a shallow "keys exist" test that can't fail. **Mitigation:** explicit normalization contract (Step 3) with real value comparisons; passes today only because real parity holds under that normalization.
- **Risk:** regenerated lockfile not committed, breaking CI's `--frozen-lockfile`. **Mitigation:** explicit verification step to run `pnpm update @fleet-works/suite-nav --filter @fleet-works/ui` and commit the resulting `pnpm-lock.yaml`.
- **Risk:** unnamed/relative-root Vitest projects silently fail to run (the exact defect found in v2). **Mitigation:** Step 1 now mandates explicit `name` + absolute `root`; Verification Steps include actually running `pnpm test` from a clean state, not just dry-run checks.

## ADR

- **Decision:** Adopt Vitest 4 as the monorepo-wide test framework via a single root `vitest.config.mts` using named, absolute-rooted `test.projects` (`suite-nav`: `node` environment; `ui`: `jsdom` + Testing Library), run through the existing `turbo run test` task — after fixing the `ui` → `suite-nav` workspace resolution at the **resolver layer** (`pnpm-workspace.yaml`'s `linkWorkspacePackages: true` + `saveWorkspaceProtocol: false`), not by editing `packages/ui/package.json`.
- **Drivers:** ESM/TS-native tooling matching the repo's `"type": "module"` + tsup + TypeScript 5.9 stack; one consistent framework and one config file across packages; CI already invokes `pnpm test` and needs a real signal against the actual local `suite-nav` source; the fix must not touch the published npm manifest, since this repo's release path (`changeset publish` → plain `npm publish`) does not rewrite `workspace:` specifiers and has already shipped a broken release once (commit `372678d`) for exactly that reason.
- **Alternatives considered:** Jest (rejected — ESM friction against `"type": "module"`, redundant transform pipeline vs. tsup/esbuild). Node built-in `node:test`, including the `node:test`-for-`suite-nav`/Vitest-for-`ui` hybrid (rejected — `ui`'s two verified blockers: cannot exercise `AppSwitcher`'s click-gated menu content, and cannot resolve this repo's existing `.js`-specifier convention; the hybrid's only claimed advantage, "`suite-nav` stays dependency-free," is not a real differentiator since devDependencies never appear in a published consumer's dependency graph).
- **Why chosen:** Vitest is the only option that covers `ui`'s real interactive surface (a closed-by-default menu that must be clicked open) and resolves the repo's existing import style unmodified. The dependency cost is honestly devDependencies-only on both packages plus root — not oversold as "zero-dependency for suite-nav," since that framing doesn't survive scrutiny of what `devDependencies` actually means for a consumer.
- **Consequences:** `pnpm-workspace.yaml` gains `linkWorkspacePackages: true` + `saveWorkspaceProtocol: false` (no `package.json` changes); root gains `vitest` devDependency and a scoped `test.inputs` entry (not `globalDependencies`) in `turbo.json`; `suite-nav` gains a `vitest` devDependency; `ui` gains `vitest`, `@types/node@^22`, `jsdom@^29`, `@testing-library/react@^16`, `@testing-library/dom`, and a minimal `src/vitest.setup.ts` (RTL cleanup only — deliberately no `@testing-library/jest-dom`, unused by the planned tests) as devDependencies; `turbo run test` now does real work; `pnpm-lock.yaml` must be regenerated and committed via `pnpm update @fleet-works/suite-nav --filter @fleet-works/ui` (a plain `pnpm install` won't apply the resolver change, and can silently *revert* it later if `suite-nav`'s version drifts outside `ui`'s range — see Risks); the published npm manifests for both packages are unchanged (verified via packed-tarball inspection, not `npm pack --dry-run` alone); `ui`'s tests resolve `suite-nav` through the workspace link's freshly-built `dist/` output rather than the published registry tarball, a known and accepted divergence from what's published at this scale (see Risks), guarded by a repeatable turbo-graph check rather than a one-time assertion.
- **Follow-ups:** see Follow-ups section above.
